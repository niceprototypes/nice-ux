Eight cache layers can hold stale state in a Nice workspace. Three workspace-level `ntk` operations clear most of them; the rest belong to other owners (the consumer's `npm install`, npm itself, the user's browser). This page maps which tool clears which layer and gives workflow recipes for the common "something is stale" symptoms.

---

## The eight layers

| # | Layer | Path | Cleared by |
|---|---|---|---|
| 1 | Global npm cache | `~/.npm/_cacache` | `npm cache clean --force` |
| 2 | Consumer `node_modules` + lockfile | `<consumer>/node_modules`, `<consumer>/package-lock.json` | `rm -rf node_modules package-lock.json && npm install` (or `website` `npm run clean`) |
| 3 | Build-tool on-disk caches (webpack, Vite, …)¹ | `<consumer>/node_modules/{.cache, .vite, …}` | `ntk --clean` |
| 4 | Linked package singleton conflicts | `<linked-pkg>/node_modules/{react,styled-components,…}` | `ntk --dedupe` |
| 5 | nice-* package dists | `<nice-pkg>/dist/` | each package's `npm run build`, or `ntk --build-all` |
| 6 | Generated source (nice-styles only) | `nice-styles/src/generated/` | `nice-styles`'s `npm run build` (runs `clean.ts` first) |
| 7 | Dev-server process (in-memory module graph + held port) | running webpack-dev-server / Vite | `ntk --clean` kills processes on declared ports; manual restart after |
| 8 | Browser module cache | RAM in the browser tab | hard reload (Cmd+Shift+R) |

¹ `ntk --clean` currently knows about `node_modules/.cache` (webpack) and `node_modules/.vite` (Vite). Other framework caches — Next.js `.next/cache`, Remix `build/`, Astro `dist/`, Parcel `.parcel-cache` — are **not** covered until their path is added to `CACHE_DIRS` in `toolkit/src/linking/cache-cleaner.js`. Adding a new framework to the workspace requires that single edit.

## The three `ntk` operations

`ntk --clean`, `--dedupe`, and `--build-all` are the workspace-level toolkit operations. They do not overlap. Each addresses a distinct layer at a distinct location. Mistaking one for another produces silent failure.

### Distinct targets

```bash
ntk --clean    →    <consumer>/node_modules/{.cache, .vite} + processes on declared ports    (layers 3 + 7)
ntk --dedupe       →    <linked-pkg>/node_modules/<singleton>                                     (layer 4)
ntk --build-all       →    <linked-pkg>/dist/                                                        (layer 5)
```

### Side-by-side

| Command | What it does | What it does **not** do |
|---|---|---|
| `ntk --clean` | Discovers each consumer's dev-server ports (parses `.env` `PORT=` entries and `package.json` script `-p`/`--port` flags), kills any process bound to those ports, then wipes webpack `.cache` and Vite `.vite` from every consumer's `node_modules` | Doesn't rebuild anything. Doesn't touch linked package internals. Doesn't reinstall. Doesn't restart killed servers. |
| `ntk --dedupe` | Removes duplicate `react` / `react-dom` / `styled-components` / etc. from every linked nice-* package's `node_modules` | Doesn't rebuild any dist. Doesn't touch consumer caches. Doesn't reinstall. |
| `ntk --build-all` | Walks registry tier order, runs `npm run build` in every linked nice-* package | Doesn't clear any cache. Doesn't touch consumer `node_modules`. Doesn't restart dev servers. |

The port-kill in `ntk --clean` exists because a running dev server holds an in-memory module graph and repopulates its on-disk cache the moment it's wiped. Wiping cache without killing the server is a no-op against the observable symptom. Use `--no-kill` to wipe caches only (e.g. CI environments).

### How they combine

For the "everything is stale" reset, the three are chained in this order:

```bash
ntk --clean    # kill dev servers + invalidate layer 3
ntk --dedupe       # resolve layer 4 singleton drift
ntk --build-all       # rebuild layer 5 in tier order
```

Then restart any dev server (`npm run dev` in each consumer) and hard-reload the browser tab.

**Order matters:**

- **`--clean` first** so the consumer's dev server is killed and its build-tool analysis is invalidated before the new dist appears.
- **`--dedupe` before `--build-all`** so singleton cleanup doesn't run *after* a build that expected the singletons in place.
- **`--build-all` last** because it produces the artifact every later step reads.

## What the three `ntk` operations do **not** touch

These belong to other owners:

| Concern | Tool | Owned by |
|---|---|---|
| Consumer `node_modules` reinstall (layer 2) | `npm install` per consumer, or `website`'s `npm run clean` | the consumer |
| Global npm cache (layer 1) | `npm cache clean --force` | npm itself |
| Restarting a killed dev server (after `--clean`) | `npm run dev` (or equivalent) in each consumer | the user |
| Browser tab module cache (layer 8) | hard reload | the user |

## Workflow recipes

#### Dev server is serving stale code after editing a linked package

```bash
ntk --clean
```

Then restart the dev server (`npm run dev` inside the consumer) and hard-reload the browser tab. `ntk --clean` killed the old process and wiped the cache; you bring the server back up when ready.

#### "Invalid hook call" or styled-components context mismatch

```bash
ntk --dedupe
```

The classic duplicate-React-instance error. See [Toolkit](/docs/configuration-toolkit--docs) for the underlying cause.

#### Consumer reports a missing export from a foundation package after a refactor

```bash
ntk --build-all
```

The consumer is reading an older `dist/` than the source now produces. Rebuild every linked package in tier order.

#### Fresh clone of the workspace

```bash
# In each consumer (website, storybook, website-viveka, …)
npm install

# Once, anywhere in the workspace
ntk --build-all
```

The `prepare` hook no longer rebuilds linked packages on consumer installs (see `manifest/.nice/reports/npm-install-breaks-consumers.md`). New clones must build dists explicitly.

#### Nuclear: I don't know what's wrong

```bash
ntk --clean
ntk --dedupe
ntk --build-all
```

Restart every dev server. Hard-reload every open browser tab.

If that doesn't fix it, escalate to a per-consumer reinstall (`rm -rf node_modules package-lock.json && npm install`) before reaching for `npm cache clean --force` — the global npm cache is almost never the cause.

## Why three `ntk` operations and not one

Each addresses a distinct concern with a distinct target directory and a distinct trigger symptom. A single umbrella verb would have to either over-fire (touch directories the symptom doesn't need) or under-fire (miss the directory the symptom does need). The three verbs are exhaustive for the workspace-level operations they cover and orthogonal to one another. Concerns outside the triad — consumer `node_modules` reinstall, global npm cache, browser hard reload — are owned by other tools and intentionally not pulled in.
