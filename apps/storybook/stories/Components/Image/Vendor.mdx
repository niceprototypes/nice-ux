<Ink as="h3">Why a separate vendor package</Ink>

<Ink>Vendor packages are containers for convenient, stable third-party plugins that provide</Ink>
<Ink weight="semibold">media, not logic</Ink>
<Ink>\u2014 concrete photo sources and icon sets. Encapsulating them outside the system keeps the host component (<code>@niceprototypes/image</code>) agnostic of any specific third-party dependency, while still letting that third party conveniently address a real need \u2014 in this case, photography.</Ink>

<Ink>The host exposes a <code>vendor</code> flag and a <code>registerVendorResolver</code> hook. The peer package is the only place a concrete source is referenced (currently <code>picsum.photos</code>; later this may be a paid CDN, an Unsplash adapter, or any other media source). Swapping, supplementing, or removing the third-party dependency later requires no changes to the host component or to any consumer call site.</Ink>

<Ink>The same pattern applies to <code>@niceprototypes/icon</code> / <code>@niceprototypes/icon-vendor</code> for iconography.</Ink>

<Ink as="h3">Setup</Ink>

<Ink>Import the vendor package once at the application entry point. The import has a side effect: it registers the resolver with <code>@niceprototypes/image</code>.</Ink>

```tsx
// app entry
import "@niceprototypes/image-vendor"
```

<Ink as="h3">Usage</Ink>

<Ink>When <code>vendor</code> is set, <code>src</code> is treated as the vendor's identifier (a <code>picsum</code> id) rather than a URL. Omit <code>src</code> to let the vendor return a random image. <code>width</code> and <code>height</code> are forwarded to the resolver as the requested asset size.</Ink>

<Ink as="h3">Direct URL access</Ink>

<Ink>When a raw URL string is needed (e.g. an <code>imageUrl</code> prop on another component), call the resolver directly:</Ink>

```tsx
import { resolveVendorImage } from "@niceprototypes/image-vendor"

const url = resolveVendorImage({ src: "10", width: "800px", height: "600px" })
// → "https://picsum.photos/id/10/800/600"
```
